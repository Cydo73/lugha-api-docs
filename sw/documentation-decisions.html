Maamuzi ya nyaraka¶

Niliandika kurasa hizi kama mfano wa jinsi ninavyoandika nyaraka za API kwa ajili ya developers. Ukurasa huu unaeleza maamuzi niliyofanya, ili uweze kutathmini namna ninavyofikiri pamoja na jinsi ninavyoandika.

Kwa nini quickstart inakuja kwanza¶

Mtu anayekagua API anataka uthibitisho kwamba inafanya kazi kabla ya kusoma kitu kingine. Quickstart inawezesha request halisi kuanza kufanya kazi ndani ya dakika chache, kisha inaeleza kila field katika response. Kila ukurasa mwingine unaunganisha tena na ukurasa huo.

Kwa nini mifano ni faili halisi¶

Code iliyo kwenye kurasa hizi inatoka moja kwa moja kwenye folda ya examples. Niliendesha kila mfano dhidi ya service inayofanya kazi: curl, Python na JavaScript. Nyaraka zinaonyesha code ileile iliyotekelezwa, na hakuna nakala ya pili inayoweza kupitwa na wakati. Sample code inayotofautiana na nyaraka ni mojawapo ya sababu zinazofanya nyaraka za developers zipoteze uaminifu.

Kwa nini errors zina ukurasa wake¶

Errors ndizo sehemu ambayo developers hutumia muda wao mwingi wa debugging. Kila failure hutumia muundo mmoja, wenye type ya kuamua hatua inayofuata, message kwa ajili ya watu na request_id kwa ajili ya support. Jedwali linaonyesha ni errors zipi zinafaa kujaribiwa tena, kwa sababu hilo ndilo swali ambalo developer huwa nalo wakati huo.

Kwa nini reference inazalishwa¶

API reference inatoka kwenye openapi/openapi.yaml, na faili hiyo hutolewa kutoka kwenye code ya service. Ukaguzi wa continuous integration hushindwa ikiwa faili hiyo haijasasishwa. Ningependelea kueleza API kwa maandishi na kuacha tool iorodheshe parameters, kwa sababu kunakili parameters kwa mkono ndiko kunakosababisha references kuwa na makosa.

Kwa nini model ni stub¶

Sina model halisi, na kubuni tabia ambayo siwezi kuithibitisha kungefanya nyaraka hizi zisiwe za kuaminika. Stub inarudisha text inayotabirika, hivyo kila response kwenye kurasa hizi ni sawa kabisa na utakayopata ukiendesha request. Tokenizer ni rahisi kwa sababu hiyo hiyo, na ukurasa wa tokens unasema hivyo wazi.

Kwa nini tokens na regions zimepewa kipaumbele¶

Kwa developers wanaojenga mifumo kwa lugha za Kiafrika, maswali mawili huibuka mapema: maandishi yao yatatumia tokens ngapi, na data yao itachakatwa wapi. Niliongeza endpoint ya kuhesabu tokens na parameter ya region ili kutoa nafasi ya maswali hayo ndani ya nyaraka. Haya ni maamuzi ya mfano ya muundo wa mfumo huu, si madai kuhusu service yoyote halisi.

Nilichoacha kwa makusudi¶

Niliondoa streaming, official SDK packages, billing na pagination. Seti ndogo ya kurasa zilizofanywa vizuri ni muhimu zaidi kuliko seti kubwa iliyofanywa kwa haraka. Streaming ingekuwa nyongeza yangu inayofuata, kwa sababu inabadilisha jinsi quickstart inavyoonekana.

Ningefanya nini na bidhaa halisi¶

Ningekaa na engineers na kusoma code kabla ya kuandika hata neno moja. Ningeendesha kila mfano mwenyewe, na ningetumia support tickets pamoja na data ya matumizi kuamua nini cha kuandika kwanza. Pia ningedumisha changelog, ili developers waweze kuona kilichobadilika kati ya versions.
