Décisions de documentation¶

J’ai rédigé ces pages comme exemple de la manière dont je documente une API pour les développeurs. Cette page explique mes choix afin que vous puissiez évaluer aussi bien ma réflexion que ma rédaction.

Pourquoi le guide de démarrage rapide vient en premier¶

Une personne qui évalue une API veut vérifier qu’elle fonctionne avant de lire quoi que ce soit d’autre. Le guide de démarrage rapide permet d’exécuter une véritable requête en quelques minutes, puis explique chaque champ de la réponse. Toutes les autres pages y renvoient.

Pourquoi les exemples sont de vrais fichiers¶

Le code présenté sur ces pages provient directement du dossier examples. J’ai exécuté chacun des exemples avec le service en cours d’exécution : curl, Python et JavaScript. La documentation montre exactement le code qui a été exécuté, sans seconde copie susceptible de devenir obsolète. Un exemple de code qui diverge de la documentation est l’une des façons les plus courantes par lesquelles la documentation destinée aux développeurs perd leur confiance.

Pourquoi les erreurs ont leur propre page¶

Les erreurs sont l’un des principaux endroits où les développeurs passent leur temps de débogage. Chaque échec utilise la même structure, avec un type permettant de déterminer le traitement à effectuer, un message destiné aux utilisateurs et un request_id pour le support. Le tableau indique quelles erreurs peuvent justifier une nouvelle tentative, car c’est la question qu’un développeur se pose réellement à ce moment-là.

Pourquoi la référence est générée automatiquement¶

La référence de l’API provient de openapi/openapi.yaml, et ce fichier est généré à partir du code du service. La vérification d’intégration continue échoue si le fichier n’est pas à jour. Je préfère expliquer l’API en prose et laisser un outil répertorier les paramètres, car copier les paramètres manuellement est l’une des principales causes d’erreurs dans les références.

Pourquoi le modèle est un stub¶

Je ne dispose pas d’un véritable modèle, et inventer un comportement que je ne peux pas vérifier rendrait cette documentation peu fiable. Le stub renvoie un texte prévisible, de sorte que chaque réponse présentée sur ces pages correspond exactement à ce que vous obtenez lorsque vous exécutez la requête. Le tokenizer est simple pour la même raison, et la page consacrée aux tokens l’indique clairement.

Pourquoi les tokens et les régions sont mis en avant¶

Pour les développeurs qui travaillent avec des langues africaines, deux questions se posent rapidement : combien de tokens leur texte utilisera et où leurs données seront traitées. J’ai ajouté un endpoint de comptage des tokens et un paramètre region afin d’apporter une réponse à ces questions dans la documentation. Il s’agit de choix de conception illustratifs pour cet exemple, et non d’affirmations concernant un service réel.

Ce que j’ai volontairement laissé de côté¶

J’ai volontairement laissé de côté le streaming, les packages SDK officiels, la facturation et la pagination. Un petit ensemble de pages bien réalisées est plus utile qu’un grand ensemble produit rapidement. Le streaming serait mon prochain ajout, car il modifie la manière dont se présente un guide de démarrage rapide.

Ce que je ferais avec un produit réel¶

Je travaillerais avec les ingénieurs et lirais le code avant d’écrire le moindre mot. J’exécuterais moi-même chaque exemple et j’utiliserais les tickets de support ainsi que les données d’utilisation pour décider de ce qu’il faut documenter en priorité. Je tiendrais également un changelog afin que les développeurs puissent voir ce qui a changé entre les versions.
